# Known Implementation Bugs — PAC-ID Resolver v2 Reference Implementation

These were found while cross-checking this spec against the Python reference implementation ([`retothuerer/LabFREED`](https://github.com/retothuerer/LabFREED)). They are **not** reflected in the spec — the spec describes the intended behavior; these are bugs to fix in the implementation so it actually matches.

The actual target for this spec is branch [`json-ld_and_get_request`](https://github.com/retothuerer/LabFREED/tree/json-ld_and_get_request) (soon to be published as `labfreed` 1.0.0), not `main`. Each item below notes its status on that branch specifically.

1. **`if: "False"` doesn't disable a block.** *(still present on `json-ld_and_get_request`)*
   Bare `True`/`False` literals in `resolver_config.py` (`cit_v2.py` on `main`) get turned into quoted Python strings before `eval()`, and non-empty strings are always truthy — so `"False"` behaves identically to `"True"`. The tokenizer/expression-builder logic is unchanged between `main` and `json-ld_and_get_request`.

2. **The shipped `tests/test_resolver/cit.yaml` mostly doesn't match anything.** *(still present on `json-ld_and_get_request` — file is byte-identical to `main`)*
   It uses single-quoted bracket keys like `$.categories['-MD']` throughout, but the convenience-substitution regex only rewrites double-quoted brackets (`["..."]`) into a real filter query — single-quoted brackets fall through to plain (non-matching) field lookup on a list. 5 of its 7 rule blocks never fire. `tests/test_resolver/test_cit_v2.py` and `test_full_resolver.py` are empty, so nothing catches this.

   Design intent (per Reto): the `[key]` bracket-key shorthand is a **local, Python-side authoring convenience only** — it must already be substituted into the real `[?(@.key == key)]` pattern by the time a resolver configuration is requested/distributed (e.g. served as the Global Resolver Configuration, or otherwise shared). It is never meant to appear in a distributed/served resolver configuration. This means, beyond fixing the single-quote gap itself, there should be a publish/normalization step that expands the shorthand before a configuration is served — check whether one currently exists, since right now the shorthand appears to be evaluated at read-time rather than expanded at write/publish-time. (Consistent with this: `examples/resolver_config_demo.yaml` on `json-ld_and_get_request` already only uses full `[?(@.key == "...")]` syntax, never the shorthand.)

3. **Inconsistent extension `data` field naming.** *(fixed on `json-ld_and_get_request`)*
   On `main`, `TREX_Extension` exposes `data` via `@computed_field`, but the generic `Extension` class only had a plain `@property` (invisible to `model_dump()`) — so its actual JSON key was `data_`. On `json-ld_and_get_request`, the generic `Extension` class now also marks `data` with `@computed_field`, so `data` is consistently queryable across extension types. Minor leftover: the raw `data_` field still also appears in `model_dump()` output alongside `data` (harmless duplication, not a correctness issue).

4. **Crashing extension syntax + broken error message.** *(fixed on `json-ld_and_get_request`)*
   On `main`, `name$type:value` (no `/`) raised `ValueError` with an unformatted string literal — `'extension number {i}, must have name and type'` (`{i}` never interpolated). On `json-ld_and_get_request`, `Extension.name`/`.type` are now `str | None`, the `raise` was removed, and an extension with neither name nor type is valid (just a RECOMMENDATION-level validation message) — its `data` becomes the whole unparsed string.

5. **`PAC_CAT.from_url()` silently downgrades to a plain `PAC_ID`** when there are no category segments, rather than returning a `PAC_CAT` with `categories: []`. *(still present on `json-ld_and_get_request` — `url_parser.py`'s `if pac_cat.categories: pac_id = pac_cat` logic is unchanged)* `.to_dict()` then has no `categories` key at all instead of an empty array — inconsistent with the documented JSON contract.

6. **Resolver configurations lose supply-order precedence.** *(new on `json-ld_and_get_request`)*
   `PAC_ID_Resolver` now stores its resolver configurations in a Python `set()` (`self._resolver_configs = set(resolver_configs)`, `resolver.py`) rather than a list, apparently to deduplicate identical configurations (`ResolverConfig.__hash__`/`__eq__` were added for this — the code comment acknowledges equality-based dedup "does not work" in some cases). A `set` does not preserve insertion order, so the precedence of explicitly-supplied resolver configurations (first supplied = highest precedence, per the spec) is no longer guaranteed — this contradicts the intended/documented behavior. Recommend an order-preserving, dedup-on-insert structure instead (e.g. a `dict` keyed by identity/hash, or a list with a manual dedup check).

7. **Note, not a bug — Global Resolver Configuration endpoint changed.** On `json-ld_and_get_request`, `_get_issuer_resolver_config` now tries `https://pac.{issuer}/resolver_config.yaml` (v2 YAML) first, falling back to the legacy `https://pac.{issuer}/coupling-information-table` (v1 CSV) only if that fails. This is reflected in the spec already — noted here just so it isn't mistaken for a regression when comparing against `main`, which only knew the single legacy URL.

8. **Note, not a bug — named category fields (`model_number`, `serial_number`, etc.) are a Python-only convenience, not part of the JSON contract.** The [PAC-CAT spec](https://github.com/ApiniLabs/PAC-CAT) only defines category segments by their GS1-style numeric key (e.g. `240`, `21`), with human-readable labels ("Model code", "Serial number") appearing only as prose, not as a formal field-name mapping. The Python `Material_Device`/`Material_Substance`/etc. pydantic classes additionally expose these as named fields (`model_number`, `serial_number`, ...) for ergonomic access from Python code, and these names do appear in `model_dump()` output — but a resolver configuration authored against this spec MUST NOT rely on them, since another (non-Python) `PAC-ID Resolver` implementation has no reason to replicate them. The spec's JSON serialization table was corrected to only document `key` + `segments` (generic, GS1-key-based) for categories; all examples now access category segment values via `segments[?(@.key == '...')]`, never via a named field.

9. **Missing in Python — `as_url` field.** The spec now defines a top-level `as_url` field in the JSON serialization of a `PAC-ID` (the `PAC-ID` re-serialized as a URL string, including extensions — equivalent to `PAC_ID.to_url()`). Neither `PAC_ID.to_dict()`/`model_dump()` on `main` nor on `json-ld_and_get_request` currently include this field — it needs to be added (e.g. as a `@computed_field` calling `self.to_url()`) so `{$.as_url}` and similar queries work.

10. **Missing in Python — non-scalar `template_url` substitution isn't valid JSON.** *(present on both `main` and `json-ld_and_get_request`)* `pac.to_dict()` passes a native Python `dict` (not a JSON string) into `_evaluate_jsonpath`, and `_eval_url_template` substitutes a match via plain `str(res[0])`. If a JSONPath expression in a `template_url` placeholder matches a non-scalar node (an object or array, e.g. `{$.categories[0]}`), `str()` on a Python `dict`/`list` produces Python's `repr()` — single-quoted keys/values, `None`/`True`/`False` instead of `null`/`true`/`false` — which is **not valid JSON**, even though it looks similar. The spec now requires non-scalar matches to be serialized as compact JSON text; the implementation needs to use `json.dumps(res[0])` instead of `str(res[0])` in that case to actually produce parseable JSON on the receiving end.
